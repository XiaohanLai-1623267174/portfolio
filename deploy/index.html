项目 01 · 独立开发 · 2026.06 至今

面向学院综测评奖政策的知识库 Agent（RAG 检索 + 工具调用）

政策条文繁杂、人工查阅效率低且易误读 —— 做一套能自己找文件、自己入库、只依据条文作答的 Agent，每句都能溯源到原文。

  • 文档结构化治理：pdfplumber 抽取复杂表格，LLM 清洗 Prompt + Pydantic 约束把原始 PDF 重构为 Markdown，提取 6 类业务元数据并按条文层级细粒度切分；前端一键上传即「解析 → 治理 → 入库」，带去重与切片缓存（命中即跳过解析）。
  • 混合检索与重排：Chroma(MMR) + BM25(jieba) 双路召回，LLM 改写查询补同义词；文档级路由按问题筛候选，本地 bge-reranker 重排取 Top-5。
  • Agent 化改造：把单轮问答升级为 ReAct 工具调用 Agent（LangGraph create_agent），编排 find_pdf / ingest_pdf / search_knowledge 三个工具，支持「说一句话就完成 找文件 → 入库 → 作答」；每轮设工具步数预算与超预算中止，避免自调用烧穿额度。
  • 全链路流式：用 LangGraph 多模式流式把节点级与 token 级事件合成一套 SSE —— token 逐字推送、命中工具轮发 token_reset 撤回模型前言、tool_call 带「第 n/8 步」进度、终态 answer 幂等覆盖防重复。
  • 可溯源与渲染一致性：检索结果自带结构化来源（文件名 / 小节路径 / 原文片段），单独发 sources 事件渲染可折叠来源清单、与正文解耦；前端 v-html 出口过 DOMPurify 消毒。

方法 · 项目里的真实链路

从一句提问，到一次可核对的工具调用

下面四步不是事后总结的方法论，是这个项目里实际跑通的流水线。每一步都留下可检查的产物，而不是只给结论。

01

治理

政策 PDF 版式复杂（跨页表格、多层条文编号）。先用 pdfplumber 抽表格，再用 LLM 清洗 + Pydantic 约束成结构化 Markdown，提取 6 类元数据并按条文层级切分；同一份文件二次上传命中切片缓存，跳过解析。

02

召回与重排

单路向量召回会漏掉同义表述。改为 Chroma(MMR) + BM25(jieba) 双路召回，LLM 改写查询补同义词，先按问题筛出候选文档，再用本地 bge-reranker 重排取 Top-5。

03

Agent 化

单轮问答只能回答已入库的问题。把链路交给 ReAct Agent（LangGraph create_agent）编排 find_pdf、ingest_pdf、search_knowledge 三个工具，一句话走完 找文件 → 入库 → 作答；每轮设工具步数预算，超预算即中止。生成阶段走云端 API，因此做了 key 池轮换与降级记账。

04

可溯源与验证

「有依据」不能靠模型自述：检索结果单独发 sources 事件渲染可折叠来源清单，正文 [n] 角标与来源强对齐，编造编号显式标「无依据」；前端 v-html 出口过 DOMPurify，每个功能配「装置 + 反向对照」防回归。

一句话完成 找文件 → 入库 → 作答 追问误判 4/7 → 0/7 每个降级原因都有人话说明

案例

面向学院综测评奖政策的知识库 Agent

唯一一个我从头做到尾的项目，所以这里把「为什么这样做」写清楚：约束在哪、砍掉了什么、哪一处是靠可核验的证据确认改对了。

背景
学院综测与奖学金评定政策条文繁杂，学生和辅导员都靠人工翻 PDF，效率低且容易误读。
问题
要让系统说出的每一句都能回到原文出处；问到条文之外时必须明确拒答；还得能自己找到没入过库的文件，而不是让人先手动上传再提问。
我的角色
独立完成：文档治理管线、混合检索与重排、Agent 工具编排与流式协议、拒答与溯源策略、后端接口与前端界面。
约束
个人项目、没有标注数据集；政策 PDF 版式复杂（跨页表格、多层编号）；重排模型只能本地跑；工具调用必须设步数上限，否则 Agent 自调用会把额度烧穿。
过程
先把 PDF 结构化再谈检索，避免在脏文本上调召回；召回从单路向量改成双路 + 重排；多轮追问做上下文改写，7 条人工追问样本里误判从 4 条降到 0 条；再把单轮问答升级为 ReAct Agent，用步数预算约束工具自调用；流式上把节点事件与 token 事件合成一套 SSE，并用 token_reset 撤回工具轮之前的模型前言。
产出
可运行的全栈 Agent 系统（FastAPI + Vue3）、一套 PDF 自动治理管线、一套 SSE 流式协议，以及配套的回归装置与反向对照脚本。
时间

首帧 token · 中位数

3 次实测：0.85 / 0.97 / 1.30s（最小 / 中位数 / 最大），从提问到第一个 token 抵达前端。n=3，只代表本机该时段。

端到端 · 工具调用 + 回答

3 次实测：9.09 / 9.55 / 11.69s。每次含 2 次 tool_call、5 条 sources、25–27 个 token 帧，答案 94–110 字。n=3。

4/7 → 0/7

多轮追问误判

人工构造 7 条追问样本，加入上下文改写前后各测一次。样本量小，只代表这一组样本。

产出细节

把回答做成可核验的形式

这个项目真正花时间的不是接大模型，而是让「有依据」可以被检查：来源走独立的 sources 事件、与正文解耦；前端与 chat 页共用同一份 Markdown 渲染真源；v-html 出口过 DOMPurify；每个功能都有对应断言。
